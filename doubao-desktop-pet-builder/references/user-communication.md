# 用户沟通与阶段声明

## 只报告已经有证据的阶段

| 阶段 | 必需证据 | 可以怎么说 |
|---|---|---|
| 素材处理完成 | 背景键检查、透明度、锚点、联系表通过 | “素材处理与检查已通过，接下来进入工程验证。” |
| 工程检查通过 | `check`、单测、资产与体验 QA 退出码为 0 | “代码和静态检查通过，尚未证明桌宠已显示。” |
| 开发预览就绪 | `DEV_PREVIEW_READY`，首帧 `naturalWidth > 0`、素材数匹配、三个窗口、桌宠可见 | “基础开发预览已启动。它不是最终版，也尚未打包，请先试玩。” |
| 试玩确认 | 用户实际完成至少一次角色互动和一次提醒 | “基础体验已确认，可以选择继续加功能或生成可执行版。” |
| 可执行版生成 | 本轮 manifest、文件、SHA-256 与实际启动 | “可执行产物已生成；真人长时稳定性仍按清单标注。” |

进程存在、Webpack 编译完成、开发服务器有地址、`.webpack`/`out` 有文件，都不能单独支撑“启动成功”。看不到桌宠时先承认未就绪并查证，不把问题归咎于用户没注意角落或托盘。

## 开发预览就绪后的固定提醒

使用接近下面的简洁表达：

> 基础开发预览已经启动，素材显示与核心窗口已通过自动检查。这还不是最终版，也没有打包成可执行程序。请先试一次【角色互动】和一次【提醒】；我会根据试玩反馈局部调整，再生成可执行版。

随后根据角色和当前缺口主动推荐 2–4 个功能。建议必须包含入口、动作和反馈，例如狗可推荐“右键接球：冲出—叼回—摇尾巴，好感度增加”；不要只列抽象功能名，也不要重复已存在的功能。

## 禁止的表达和做法

- 不说“某个库比我写的靠谱”“太好了，先安装某库”“需要你理解一下依赖”。依赖准备是内部步骤。
- 不在 Pillow、Sharp、自写脚本之间临时换路。模板已锁定 Sharp；缺依赖时执行一次 `npm ci`，失败则报告具体阻断。
- 不用“应该出现了”“进程还在所以没问题”“缓存报错不影响”代替证据。
- 不把开发预览称为最终版，不在尚未打包时只给玩法说明。
- 不把 ZIP 当成可执行文件。Windows 先指出可直接双击的 EXE 路径；ZIP 只说明为传输用压缩包。
- 对普通用户不播报低层库名、命令切换和自我评价；进度只说当前阶段、已验证内容和下一步。

## 失败时怎么说

先写事实，再写下一步：

> 开发进程已启动，但首帧素材没有通过加载检查，因此当前不能算启动成功。我会检查素材路径、Webpack 导入和初始化日志，修好并重新验证后再请你试玩。

没有自动或真人证据时统一写“待确认”，不得写“已完成”“已修好”或“已经跑到桌面”。
